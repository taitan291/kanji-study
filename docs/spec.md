# 漢字学習サイト 仕様書（ドラフト v0.1）

最終更新: 2026-11-17
状態: ドラフト（実装はまだ行わない）

この文書は、漢字の書き取りを手書きで練習するための静的Webサイトの仕様をまとめたものです。決まっている事項と、あとで決める事項（**【未決定】** と表示）を分けて書いています。

## 1. 目的と前提

| 項目 | 内容 |
| --- | --- |
| 目的 | スマホ・iPadで漢字を手書きし、自己採点し、統計と復習で定着させる |
| 利用者 | 本人1人のみ。プロフィール（複数人の切り替え）は作らない |
| 構成 | 静的サイト。サーバー側のデータベースは使わない |
| ホスティング | Cloudflare Pages |
| ソースコード | GitHubの非公開リポジトリ |
| データ保存先 | ブラウザ内のみ（localStorage と IndexedDB） |
| 引き継ぎ | 統計データをJSONで書き出し・読み込み（読み込み時は統合） |
| 想定端末 | iPad（Safari、Apple Pencil）、スマホ（iPhoneのSafariなど）、PCのブラウザ。縦向き・横向きのどちらでも使える（第3.4） |
| URL | `https://kanji.taitan.uk`（独自ドメインのサブドメイン。第10.3） |

## 2. 画面と機能の一覧

1. **ログイン画面**（Cloudflare側で表示。第8章）
2. **ホーム画面**
   - 「出題する」「復習する」ボタン
   - 復習リストの件数と内訳（連続正解 0 / 1 / 2。第6.3）
   - 最後にJSONを書き出してからの日数（警告表示つき。第7章）
3. **出題設定画面**
   - 問題数: 10問 / 20問 / 自由設定（1〜出題範囲の問題数まで）
   - 出題範囲: 回をまたいで自由に設定できる（第9.4）
   - 出題順: ランダム（範囲の中から無作為に選び、順番もばらばらにする）
4. **解答画面**（1問ずつ、手書き。第3章）
5. **自己採点画面**（全問を解き終わった後。第4章）
6. **結果画面**（その回の正答数と、間違えた問題の一覧）
7. **統計画面**（第5章。単位は【未決定】）
8. **設定・データ管理画面**
   - JSONを書き出す / JSONを読み込む（統合）
   - 統計データをクリア
   - ペン入力のみ受け付ける（手のひらの誤タッチ防止）のオン・オフ
   - ペンの太さ
9. **漢字一覧画面**（`#/list`。ホームの「漢字一覧」から開く）
   - 問題データの漢字と読みを、回ごとにカードで並べる。カードを押すと例文（読みは太字）と意味が開く
   - 回と文字（漢字・読み・例文・意味。読みはひらがなでも可）で絞り込める
   - 「漢字を隠す」で読みだけを表示し、カードを開くと漢字が見える
   - 復習リストにある漢字には「復習」の印をつける
   - 表示中の問題だけで出題できる（ランダム順）。一覧を見るだけでは記録しない

## 3. 手書き入力

### 3.1 道具

| 道具 | 動き |
| --- | --- |
| ペン | 黒い線を書く。太さは設定で変えられる |
| 消しゴム | なぞった部分を消す |
| 全部消す | その問題のキャンバスを白紙に戻す |
| 1つ戻す | 直前の操作（ペン、消しゴム、全部消す）を1つ取り消す |

- マス目は表示しない（白紙のキャンバス）。
- 「全部消す」も「1つ戻す」で元に戻せるようにする（誤操作対策）。
- 「やり直し（戻したものを再度進める）」は必須ではない。必要になれば追加する。

### 3.2 技術的な方針

- `<canvas>` と Pointer Events（指・ペン・マウスを同じ仕組みで扱うブラウザ標準の機能）で実装する。
- 線は**画像ではなく「線の座標の列（ストローク）」として記録**する。
  - 「1つ戻す」は最後の操作を外して描き直すだけで済む。
  - 保存するデータが小さい。
  - 消しゴムも「消す線」として記録し、描き直すときに重ねる。
- 「ペン入力のみ」設定がオンのときは、Apple Pencilの入力だけを受け付け、指や手のひらのタッチは無視する。
- キャンバス上では、スクロール、ピンチによる拡大、ダブルタップによる拡大、長押しメニューが起きないようにする。
- 筆圧による線の太さの変化は任意（あると見た目がよいが、採点には不要）。

### 3.3 解答中の操作

- 「前の問題」「次の問題」で行き来でき、書いた内容は残る。
- 最後の問題で「採点へ進む」を押すと自己採点画面に移る。未記入の問題があれば確認を出す。

### 3.4 画面の大きさと向き（決定）

iPad、スマホ、PCのどれでも、縦向き・横向きのどちらでも使えるようにする（レスポンシブ対応）。

| 端末・向き | 解答画面 | 採点画面 |
| --- | --- | --- |
| iPad・PC 横向き | 本文を右、キャンバスを左に並べる | 左に意味、中央に正しい漢字（上）と手書き（下）、右に本文の3列 |
| iPad 縦向き | 本文を上、キャンバスを下に大きく | 3列のまま（幅に余裕があるため） |
| スマホ 横向き | 本文を右、キャンバスを左 | 3列（文字を小さめに） |
| スマホ 縦向き | 本文を上、キャンバスを下 | 上から本文、正しい漢字と手書きを横に並べた段、意味の順に縦に積む |

- 向きを変えても、書いた内容は消えない。線は座標で記録しているので（3.2）、新しい大きさに合わせて描き直す。座標はキャンバスの大きさに対する割合で記録する。
- 道具ボタンは指で押しやすい大きさ（目安 44px 以上）にする。
- PCではマウスで書けるようにし、キーボード操作（例: 次の問題、1つ戻す）も用意する。
- 画面の切り替えの目安は Tailwind CSS の標準の幅（`sm` / `md` / `lg`）と、向き（`portrait` / `landscape`）を使う。

## 4. 自己採点と画像の扱い

### 4.1 流れ

1. 1問ずつ、次の配置で表示する（決定）。

   | 左 | 中央 | 右 |
   | --- | --- | --- |
   | 意味 `imi` | 上: 正しい漢字 `kanji`<br>下: 自分が書いた手書き | 本文 `furu`（`yomi` は太字） |

2. 各問題に ○ または × を付ける。付け直しもできる。採点は ○ と × の2つだけで、△（部分点）は作らない（決定）。
3. 全問に ○× が付いたら「採点を確定」ボタンを押せるようにする。
4. 確定した時点で、結果を統計に記録し、**手書きのデータを削除する**。

### 4.2 IndexedDB とは

IndexedDB は、ブラウザに内蔵されている保存場所の1つです。

- localStorage と同じく、**そのブラウザの中だけ**にデータを保存します。サーバーには送られません。
- localStorage は短い文字列向けで容量も小さい（数MB程度）のに対し、IndexedDB は画像や大きなデータもまとめて保存でき、容量にも余裕があります。
- ページを再読み込みしたり、ブラウザを閉じたりしても残ります。

### 4.3 この仕組みで使う理由

手書きのデータをメモリにだけ置くと、解答中や採点中に誤ってページを再読み込みしたり、Safariがタブを閉じたりしたときに、書いた内容が消えてしまいます。そこで、

- 解答中: 1画（または一定間隔）ごとに、その回の手書きデータを IndexedDB に保存する。
- 採点の確定時: その回の手書きデータを IndexedDB から削除する。

という扱いにします。「画像は自己採点が終わるまで保持」という要件をそのまま満たします。

### 4.4 途中で中断した場合

- 起動時に、採点が終わっていない回が IndexedDB に残っていれば「続きから再開する / 破棄する」を聞く。
- 未完了の回は同時に1つまでとする（新しく始めるときは、古い回の破棄を確認する）。
- 破棄した回は統計に記録しない。

## 5. 統計

### 5.1 方針

統計の単位（漢字ごと、学年・単元ごと、日ごと など）は【未決定】です。そのため、**集計済みの数字ではなく、1問ごとの解答記録（生データ）をすべて残しておく**設計にします。こうしておけば、単位をあとで決めても、過去の記録から計算し直せます。

### 5.2 記録する内容（1問の解答ごと）

| 項目 | 例 | 説明 |
| --- | --- | --- |
| `id` | `"7f3c…"` | この記録の一意なID（UUID） |
| `questionId` | `"49-1"` | 問題のID（回の番号-問題番号。第9.3） |
| `sessionId` | `"a91e…"` | どの回の出題か |
| `mode` | `"normal"` / `"review"` | 通常出題か復習か |
| `correct` | `true` | ○ なら true |
| `answeredAt` | `"2026-11-17T13:45:00+09:00"` | 採点を確定した日時 |

回（セッション）ごとにも、開始日時・問題数・設定を記録します。

### 5.3 表示する統計（決定）

| 単位 | 表示する内容 |
| --- | --- |
| 漢字（問題）ごと | 出題回数、正答回数、正答率、○×の履歴 |
| 回（第49回など）ごと | 解答数、正答回数、正答率 |
| 全体 | 累計の解答数と正答率、直近の出題の結果 |

**苦手な漢字**: 正答率の低い順に並べた一覧を出す。

- 出題回数が少ない問題で順位が大きく動かないよう、2回以上解いた問題だけを対象にする（回数は設定値）。
- 正答率が同じなら、間違えた回数の多い方を上にする。
- 一覧から、その漢字だけを選んで出題できるようにする。

### 5.4 決めていないこと

- 日ごと・週ごとの集計や、正答率の推移のグラフは今は作らない。生データを残すので、あとから足せる。

## 6. 復習のルール

方針は任されたため、以下のように設計します。使い方は**テスト前夜の一夜漬けが基本**なので、日付で間隔を空ける方式（1日後、3日後など）は使いません。**回数だけ**で判断し、同じ夜のうちに何回でも回せるようにします。

### 6.1 ルール

1. 通常出題でも復習でも、**×が付いた問題は復習リストに入る**（連続正解 0）。
2. 復習リストの問題に ○ が付くと、連続正解が1つ増える。
3. **連続正解が 2 になったら、復習リストから外れる（卒業）**。連続正解の回数は設定値で、初期値 3 から 2 に変更した（2026-11-17、ユーザー要望）。
4. 途中で × が付くと、連続正解は 0 に戻る。
5. 1回の出題（10問など）の中で同じ問題は1度しか出さないので、連続正解は「別々の回で続けて正解した数」になる。
6. 卒業した問題も、通常出題で再び × になれば、もう一度 0 から復習リストに入る。
7. 日付は判断に使わない。今夜のうちに2回続けて正解すれば、今夜のうちに卒業できる。

連続正解の回数（初期値 2）は、使ってみて調整できるよう設定値として持ちます。

### 6.2 採点直後の「間違えた問題だけもう一度」

- 結果画面に「間違えた問題だけもう一度」ボタンを置く。押すと、その回で × だった問題だけで、すぐに次の回を始める。
- これも通常の1回として記録するので、ここでの ○ は連続正解に数える。
- 全問 ○ になるまで繰り返せば、一夜漬けの流れ（解く → 間違えたものを解き直す）をそのまま回せる。

### 6.3 復習の出題

- ホーム画面の「復習する」は、復習リストの問題から出題する。
- 問題数は通常出題と同じく 10 / 20 / 自由設定。リストの方が多い場合は、**連続正解の少ないもの**、次に**間違えた回数の多いもの**を優先する。
- ホーム画面には、復習リストの件数と、その内訳（連続正解 0 / 1 / 2）を表示する。

### 6.4 復習の状態は解答記録から計算する

復習リストの中身（各問題の連続正解の数）は、別に保存せず、**5.2の解答記録を古い順にたどって毎回計算**します。こうすると、JSONの統合（第7章）で記録を足し合わせても、復習の状態が食い違いません。

## 7. データの保存と引き継ぎ

### 7.1 保存場所

| データ | 保存先 | 寿命 |
| --- | --- | --- |
| 解答記録・回の記録 | IndexedDB | ずっと（クリアするまで） |
| 設定（ペンの太さなど） | localStorage | ずっと |
| 解答中・採点中の手書きデータ | IndexedDB | 採点の確定まで |
| 最後にJSONを書き出した日時 | localStorage | ずっと |
| 問題データ | サーバーから取得（オフライン用にキャッシュ） | — |

### 7.2 iPad / iPhone の Safari でデータが消える問題

Safari には、**7日間そのサイトを開かないと、そのサイトが保存したデータ（localStorage、IndexedDB など）を消す**仕組みがあります。対策は次の3段構えです。

1. **ホーム画面に追加して使う（PWA化）**
   ホーム画面に追加したWebアプリは、この7日ルールの対象外になります。サイトにマニフェストとアイコンを用意し、初回に「ホーム画面に追加してください」という案内を出します。
2. **`navigator.storage.persist()` を呼ぶ**
   ブラウザに「このサイトのデータは消さないで」と依頼する標準の機能です。許可されたかどうかを設定画面に表示します。
3. **JSONの書き出しを保険にする**
   最後に書き出してから7日以上たったら、ホーム画面に「バックアップを書き出しましょう」と表示します。

### 7.3 JSONの書き出し

```json
{
  "format": "kanji-study-backup",
  "schemaVersion": 1,
  "exportedAt": "2026-11-17T13:45:00+09:00",
  "sessions": [ { "id": "…", "startedAt": "…", "mode": "normal", "count": 10 } ],
  "attempts": [ { "id": "…", "questionId": "49-1", "sessionId": "…", "mode": "normal", "correct": true, "answeredAt": "…" } ]
}
```

- 中身は**集計した数字ではなく生データ**（1問ごとの、問題IDと採点した時刻と○×の記録）にする。統計は読み込んだ側で計算し直す。
- ファイル名は `kanji-backup-2026-11-17.json` のように日付を入れる。
- 手書きのデータと設定は含めない（設定は端末ごとに違ってよいため）。
- iPadでは共有シート経由で「ファイル」アプリやAirDropに保存できるようにする。

### 7.4 JSONの読み込み（統合）

読み込んだデータは、今あるデータに**足し合わせます**（上書きはしない）。

| 対象 | 統合のルール |
| --- | --- |
| 解答記録 `attempts` | `id` が同じものは同一として1件にまとめる。違うものはすべて追加する |
| 回の記録 `sessions` | 同上 |
| 復習の状態 | 統合後の解答記録から計算し直す（6.4） |

- 同じファイルを2回読み込んでも、件数は増えない（`id` で重複を除くため）。
- 読み込み前に「追加される件数 / 重複していた件数」を表示し、確認してから反映する。

### 7.5 スキーマのバージョン

- `schemaVersion` が今のアプリより**古い**ファイル: 変換してから読み込む。
- `schemaVersion` が今のアプリより**新しい**ファイル: 読み込まずに「アプリを更新してください」と表示する。
- `format` が違うファイル: 読み込まない。

### 7.6 問題データとの対応

- 解答記録に、問題データにない `questionId` が含まれていても、記録は消さずに残す（統計では「削除された問題」として扱う）。
- そのため、**問題データのIDは一度決めたら変えない**ことを、問題データ形式のルールにする（第9章）。

### 7.7 統計データをクリア

- 設定・データ管理画面に置く。
- 消す対象: 解答記録、回の記録、復習リスト（計算元が消えるので自動的に空になる）、未完了の回の手書きデータ。
- 消さない対象: 設定、問題データ。
- 押したときの流れ:
  1. 「消す前にJSONを書き出しますか？」と書き出しボタンを出す。
  2. 確認として「クリア」と入力させる（誤操作防止）。
  3. 削除する。元には戻せない（書き出したJSONを読み込めば戻せる）。

## 8. ログインと問題データの非公開

### 8.1 方針

- GitHubのリポジトリは**非公開**にする。問題データもリポジトリに含めてよい。
- 公開されたサイトでは、Cloudflare Pages Functions（Pagesに付いている、リクエストごとに小さなプログラムを動かせる機能）の**ミドルウェア**で、全ページと問題データへのアクセスにユーザー名とパスワードを求める。
- メールアドレスは集めない。利用者は1人なので、ユーザー名とパスワードは1組だけ。

### 8.2 認証情報の置き場所

- コードに直接書く（ハードコード）ことも可とする。
- ただし少しの手間で改善できるため、**Cloudflare Pagesの環境変数（シークレット）に置く**ことを推奨する。
  - 例: `AUTH_USER`、`AUTH_PASSWORD`
  - 非公開リポジトリでも、コードにパスワードが残らないので安心。
  - パスワードを変えたいときに、コードを変えずにCloudflareの管理画面で変更できる。

### 8.3 方式の候補

| 方式 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A. Basic認証 | ブラウザ標準のユーザー名・パスワード入力窓を出す | 一番簡単 | ホーム画面に追加したPWAで、入力窓が出にくい・何度も聞かれるなど、iOSでの動きが不安定なことがある |
| B. 簡単なログインフォーム＋Cookie（推奨） | 自前の小さなログイン画面で照合し、合っていれば署名付きのCookieを長期間（例: 1年）発行する | PWAでも安定して動く。一度入れればしばらく聞かれない | Aより少しコードが増える |

**決定: B（簡単なログインフォーム＋Cookie）を採用する。** 7.2のとおりPWA化が前提になるため。

### 8.4 守る範囲と注意点

- `/*`（全ページ、JavaScript、問題データのJSON）をミドルウェアで守る。ログイン画面だけは除く。
- Cloudflare Pagesのプレビュー用URL（ブランチごとに作られるURL）にも同じミドルウェアがかかることを確認する。
- 通信はHTTPS（Cloudflare Pagesは標準でHTTPS）。
- 問題データは、オフラインでも使えるよう端末にキャッシュされる。端末自体は本人のものなので許容する。
- 代わりの選択肢として Cloudflare Access（Zero Trust）もあるが、メールアドレスでの認証が基本になるため、今回は採用しない。

## 9. 問題データと出題形式

### 9.1 出題形式（決定）

- 例文 `furu` を表示し、その中の読み `yomi` の部分を**太字**にする。
- 利用者は、太字の部分にあたる漢字 `kanji` を手書きする。
- 自己採点では、手書きと `kanji` を並べて表示する。

表示の例:

> 毎朝**ガッコウ**へ歩いて通う。　→　書く答え: 学校

送りがなのある問題は、`yomi` が太字の部分だけ、`kanji` が送りがな込みになります（例: 「グラウンドを**ハシ**る。」→ 答え「走る」）。

### 9.2 データ形式（決定）

```json
{
  "49": {
    "1": { "kanji": "学校", "yomi": "ガッコウ", "furu": "毎朝ガッコウへ歩いて通う。", "imi": "勉強を教わるところ" },
    "2": { "kanji": "走る", "yomi": "ハシ", "furu": "グラウンドをハシる。", "imi": "速く進む" }
  }
}
```

| キー | 意味 |
| --- | --- |
| 1段目（`"49"`） | 回の番号（教材の「第49回」） |
| 2段目（`"1"`） | その回の中の問題番号 |
| `kanji` | 模範解答（書く漢字。送りがながあれば含む） |
| `yomi` | 例文の中で太字にする読み（カタカナ） |
| `furu` | 例文（読みの部分はカタカナのまま） |
| `imi` | 意味の説明（採点画面の左に出す） |

- 置き場所: `data/questions.json`（ログインで守る範囲に置く）。
- `yomi` は `furu` の中にちょうど1回出てくることを前提にする（太字にする位置を決めるため）。

### 9.3 問題ID

- 問題IDは「回の番号-問題番号」とする（例: `"49-1"`）。解答記録の `questionId` にはこれを使う。
- 回の番号と問題番号は一度決めたら変えない。問題を直すときは中身だけを直し、番号は使い回さない。

### 9.4 出題範囲

出題範囲は、回をまたいで自由に決められるようにする（決定）。指定のしかたは次の2つで、組み合わせられる。

| 指定のしかた | 例 |
| --- | --- |
| 始まりと終わりを指定 | 「第49回の5番」から「第51回の10番」まで（間の回はすべて含む） |
| 回を選ぶ | 第49回、第52回、第54回（飛び飛びでもよい） |

- 複数の範囲を足し合わせられる（例: 第49回5番〜第50回3番 ＋ 第53回すべて）。
- 範囲の中の問題数を表示し、問題数（10 / 20 / 自由設定）がそれより多い場合は範囲の問題数までにする。
- 範囲の中から**ランダムに**選び、出す順番もランダムにする。
- 最後に使った範囲を覚えておき、次に開いたときの初期値にする（localStorage）。

### 9.5 その他

- 教材の「訓読み」の欄（例: 唇→くちびる）は採用しない（決定）。
- ファイル全体のバージョン番号は持たせない。今の形式のままにし、形式を変えることになったら、そのときに考える。
- 教材の意味の説明は `imi` として持ち、採点画面に出す（決定。第4.1）。

## 10. 技術構成

### 10.1 決まっていること

- スタイル: Tailwind CSS
- 開発環境: `flake.nix`
  - flake-parts でまとめる
  - treefmt（treefmt-nix）で整形（例: JS/TS/CSS/JSON は Prettier または Biome、Nix は nixfmt）
  - pre-commit フック（git-hooks.nix）でコミット前に整形とチェックを実行
  - devShell に Node.js と wrangler（Cloudflareのコマンドラインツール）を入れる
- ホスティング: Cloudflare Pages（静的ファイル＋ログイン用の Pages Functions）

### 10.2 フレームワーク

**決定: Vite＋Svelte を使う。** 検討した候補は次のとおり。

| 候補 | ひとこと |
| --- | --- |
| Vite＋素のTypeScript | 一番軽い。画面が少ないので十分成り立つ。画面の状態管理は自前 |
| Vite＋Svelte | 書く量が少なく、出力も小さい。小規模アプリと相性がよい |
| Vite＋Preact | Reactと同じ書き方で軽量 |
| SvelteKit（静的出力） | ページの切り替えやPWAの仕組みが揃っているが、今回の規模には少し大きい |

手書きキャンバスはどのフレームワークでも素のcanvasで書くことになるため、差が出るのは画面の切り替えと状態管理です。

### 10.3 デプロイ

- 公開URLは `https://kanji.taitan.uk`（決定）。Cloudflare Pages の「カスタムドメイン」に `kanji.taitan.uk` を追加する。`taitan.uk` のDNSがCloudflareで管理されていれば、CNAMEは自動で作られる。
- Pages が最初に用意する `*.pages.dev` のURLにも同じログインがかかるが、普段は `kanji.taitan.uk` を使う。
- Cloudflare Pages と非公開のGitHubリポジトリを連携し、mainブランチへのpushで自動デプロイする。
- Cloudflareのビルド環境にNixはないため、ビルドは `npm run build` などNixなしで通るようにしておく（Nixは手元の開発環境用）。
- もしくは GitHub Actions でビルドし、`wrangler pages deploy` で配置する。

### 10.4 オフライン対応

- Service Worker で、アプリ本体と問題データをキャッシュする。
- 一度ログインして開けば、電波のない場所でも出題・採点・統計が使える。
